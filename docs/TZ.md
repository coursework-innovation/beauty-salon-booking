# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

**Beauty Booking · Техническое задание · версия 1.1**

## 1. Общие сведения

Наименование: Beauty Booking. Тип системы: серверное веб-приложение одного салона красоты.

Заказчик и пользователи: посетители салона, зарегистрированные клиенты, мастера и администратор.

Цель — обеспечить подбор мастера и услуги, онлайн-запись без пересечения интервалов, сопровождение визитов и управление деятельностью салона.

Система ориентирована на один салон; мультисалонность, онлайн-оплата, SMS-уведомления и интеграция с внешними CRM в исходный объём не входят.

## 2. Назначение и границы системы

- Гость изучает мастеров, услуги, стоимость, акции и публикации журнала красоты без авторизации.
- Клиент регистрируется, входит, выбирает время, записывается, просматривает историю, отменяет допустимые записи и оставляет отзыв после завершённого визита.
- Мастер управляет своими сменами, персональными тарифами, завершением визитов и публикациями работ в пределах своих прав.
- Администратор управляет данными салона, контентом и расписанием, оформляет запись для клиента и просматривает статистику.

## 3. Технологии и среда

| Компонент | Требование |
|---|---|
| Backend | Python, Flask; фабрика приложения и Blueprints auth/public/visits/manage |
| Представления | HTML, Jinja2, CSS, JavaScript; серверный рендеринг |
| СУБД | PostgreSQL 16, ограничения целостности и транзакции |
| Запуск | Dockerfile, compose.yaml, web + db; постоянный Docker volume для PostgreSQL |
| Аутентификация | bcrypt для паролей; JWT сроком 8 часов; отзыв jti при выходе; CSRF для POST-форм |
| Тестирование | unittest, интеграционные тесты, GitHub Actions |
| Совместная разработка | GitHub Issues/Projects, ветки задач → dev → main, pull request и ревью |

## 4. Роли и матрица доступа

| Действие | Гость | Клиент | Мастер | Администратор |
|---|---|---|---|---|
| Просмотр каталога/акций/журнала | Да | Да | Да | Да |
| Регистрация и вход | Да | Да | Да | Да |
| Создание записи для себя | Нет | Да | По согласованию | Да, с выбором клиента |
| Свои записи, отмена, отзыв | Нет | Да | По согласованию | По полномочиям |
| Свои смены/тарифы/работы | Нет | Нет | Да | Да |
| Управление салоном и отчёты | Нет | Нет | Нет | Да |

В исходном бэклоге описаны три авторизованные роли (client, master, admin) и гость как неавторизованное состояние. Новая регистрация всегда назначает роль client. Доступ проверяется на сервере; попытка клиента открыть /manage должна приводить к HTTP 403.

## 5. Функциональные требования и задачи проекта

### 5.1. Функциональные требования FR01–FR16

### FR01. Регистрация
Пользователь создаёт учётную запись с именем, email и паролем от 8 символов. Email уникален, поля валидируются на сервере, пароль хранится только в виде bcrypt-хеша; роль по умолчанию — client.

### FR02. Вход и выход
Авторизация по email/паролю, JWT сроком 8 часов, CSRF-защита изменяющих форм, отзыв jti при выходе. Неверный пароль — 401, отсутствие CSRF в POST — 400; после выхода прежний токен не действует.

### FR03. Каталог мастеров
Публичная главная страница, каталог и поиск по услуге, бюджету, строке q и сортировке sort. При отсутствии совпадений выводится пустое состояние; переход на неизвестного мастера — 404.

### FR04. Профиль мастера
Профиль показывает опыт, услуги, цены, портфолио, отзывы и рейтинг. Карточки мастеров ведут на профиль и запись.

### FR05. Каталог услуг
Публичный список услуг с базовыми и персональными тарифами мастеров; цена для отображения вычисляется на выбранную дату.

### FR06. Акции и цены
Применяется максимальная подходящая скидка на дату; результат SQL offers(on_day) содержит original, price, discount; денежные значения округляются до копеек. Правила суммирования скидок не предусмотрены.

### FR07. Свободное время выбранного мастера
Для выбранной услуги, дня и мастера система показывает допустимые свободные слоты с учётом длительности услуги, смен и уже существующих визитов.

### FR08. Свободное время любого мастера
Пользователь может выбрать «любой мастер»; система предлагает доступные интервалы подходящих мастеров и фиксирует конкретного исполнителя при подтверждении.

### FR09. Создание записи
Авторизованный клиент подтверждает услугу, мастера, дату и время. Сервер повторно проверяет доступность и рассчитывает стоимость; клиент не может подменить цену в форме. Одновременное бронирование пересекающихся интервалов запрещено.

### FR10. Кабинет и отмена
Клиент просматривает будущие и прошедшие визиты, календарь день/неделя, отменяет только собственные записи не менее чем за 120 минут до начала.

### FR11. Отзывы
Клиент может оставить отзыв только о своём завершённом визите; на один визит допускается один отзыв (уникальность visit_id). Оценка — от 1 до 5. Отзывы участвуют в отображении профиля/рейтинга.

### FR12. Управление сменами
Мастер управляет собственным рабочим расписанием. Изменение смены, конфликтующее с существующим визитом, отклоняется; чужие смены недоступны.

### FR13. Работа мастера
Мастер изменяет собственные тарифы, отмечает завершение визитов и публикует работы/портфолио; изменение чужого тарифа запрещено.

### FR14. Журнал красоты
Публичные публикации о трендах месяца, брендах, советах и фактах с указанием авторства; поддерживаются пустые состояния.

### FR15. Контент и история
В системе отображаются материалы и история салона; уполномоченные сотрудники управляют публикациями и акциями в рамках прав.

### FR16. Администрирование и статистика
Администратор управляет содержимым салона и записями, просматривает отчёт за период и проверяемые показатели: число записей, популярность услуг и выручку завершённых визитов, сопоставимые с данными PostgreSQL.

## 7. Логика бронирования

Интервалы занятости рассматриваются как полуоткрытые [начало, конец): соприкосновение концов не считается пересечением. База данных должна содержать ограничение no_overlap для пересекающихся визитов одного мастера. Проверка на сервере и ограничение в БД применяются совместно; при гонке из двух подтверждений одного слота один запрос успешен (303), другой получает конфликт (409).

Длительность услуг и шаг слотов задаются данными/настройками проекта. При подтверждении запись сохраняет рассчитанную на сервере стоимость; момент фиксации цены и изменение цены после бронирования требуется согласовать. Для отмены бэклог требует отдельно проверить границу 120 и 119 минут до начала: отмена разрешена при остатке не менее 120 минут, запрещена при 119 минутах. Время салона — московское (Europe/Moscow); правила хранения временных меток следует зафиксировать отдельно.

## 8. Требования к данным

Минимальная логическая модель, вытекающая из бэклога: пользователи и роли; мастера и их профили; услуги; персональные тарифы; акции; смены; визиты; отзывы; портфолио; материалы журнала/истории. Точный состав полей и связи закрепляются в db/schema.sql и docs/er.md (F04).

- users: уникальный email, роль и bcrypt-хеш пароля.
- visits: обязательные ссылки на клиента, мастера и услугу; время начала/окончания, статус и зафиксированная цена; запрет пересечения по мастеру.
- reviews: ссылка на визит с уникальным visit_id, автор и оценка/текст согласно утверждённой схеме.
- Тарифы и акции: поддержка расчёта offers(on_day), original/price/discount; денежная точность до копеек.
- Все ссылки должны обеспечиваться внешними ключами, значения статусов и диапазоны времени — ограничениями.

Демонстрационный набор F13: пять мастеров, два клиентских аккаунта, аккаунт мастера и администратора, скидка на гель-лак и вчерашний визит Ивана. Повторный seed не создаёт дубликатов. Контрольный пример F19: при действующей акции стоимость гель-лака у Анны — 1760 ₽.

## 9. Нефункциональные требования

- Безопасность: серверная проверка прав, параметризованные SQL-запросы, транзакции, bcrypt, JWT и CSRF; конфиденциальные параметры хранятся в .env и не коммитятся.
- Надёжность: данные PostgreSQL сохраняются в Docker volume после остановки и повторного запуска контейнеров.
- Наблюдаемость: /health проверяет SELECT 1 в PostgreSQL и возвращает 200 при исправной работе.
- Удобство: читаемые ошибки, пустые состояния, доступная навигация с клавиатуры, адаптивные формы и лента.
- Производительность: время ответа измеряется пять раз в T15; целевое время ответа публичного каталога, поиска и выдачи свободных окон на демоданных — до 1 секунды. Измерения документирует Олег.
- Воспроизводимость: README позволяет другому участнику запустить приложение на новом томе, выполнить seed и войти в тестовый аккаунт.
